# Cinema API

Серверна частина кінотеатру на NestJS: фільми, зали, сеанси та бронювання місць.
Дані лежать у PostgreSQL (TypeORM), схема створюється міграціями. Це друга робота курсу: код ДЗ №1 із масивами в пам'яті переведено на таблиці бази даних.

## Встановлення залежностей

```bash
npm install
```

## Змінні середовища

Скопіюй `.env.example` у `.env` і за потреби зміни значення. Файл `.env` у репозиторій не потрапляє.

```bash
cp .env.example .env
```

Приклад `.env`:

```env
# Port the HTTP server listens on
PORT=3000

# Runtime environment label (development | production | test)
NODE_ENV=development

# PostgreSQL connection. The same values are used by Docker Compose to create
# the database, by the application and by the TypeORM CLI.
DB_HOST=localhost
DB_PORT=5432
DB_USERNAME=cinema
DB_PASSWORD=cinema_password
DB_NAME=cinema
```

Змінні читає `ConfigModule` і перевіряє клас `EnvironmentVariables` (`src/config/env.validation.ts`, декоратори class-validator). Якщо будь-якої змінної `DB_*` бракує або вона некоректна, застосунок не стартує й виводить список проблем. `PORT` необов'язковий (за замовчуванням 3000). Сервіси отримують значення через `ConfigService`, а не через `process.env`.

## Підняття бази даних (Docker Compose)

```bash
docker compose up -d
```

Піднімає PostgreSQL 16 з `docker-compose.yml` (користувач, пароль, назва бази й порт беруться з `.env`). Дані зберігаються в томі `cinema_pgdata`. Зупинити: `docker compose down` (з `-v` ще й видалить дані).

## Застосування міграцій

```bash
npm run migration:run
```

Створює всі таблиці з порожньої бази. Інші команди:

```bash
npm run migration:show                              # які міграції застосовані
npm run migration:revert                            # відкотити останню міграцію
npm run migration:generate -- src/migrations/Name   # нова міграція за різницею сутностей і бази
```

Схема створюється **лише** міграціями (`synchronize: false`). Кожна міграція оборотна (`down` повертає базу в попередній стан). Застосовані міграції не редагуються: зміна схеми означає нову міграцію. Підключення для CLI описує `src/data-source.ts`, параметри підключення спільні із застосунком (`src/database/data-source-options.ts`).

## Засівання бази даних

```bash
npm run seed
```

Запускає `src/seed.ts` на порожній базі після міграцій: 2 фільми, 2 зали, 4 сеанси в різні дати (завтра, післязавтра, через 3 і через 7 днів) і 1 бронювання з двох місць. Повторний запуск дублікатів не створює: рядки мають фіксовані id й вставляються з `ON CONFLICT DO NOTHING`.

## Запуск у режимі розробки

```bash
npm run start:dev
```

Сервіс стартує на `http://localhost:3000` (порт береться зі змінної `PORT`).
Swagger-документація: `http://localhost:3000/docs`.

Інші команди: `npm run build` (збірка в `dist/`), `npm run start:prod` (запуск зібраного коду).

Повний порядок з нуля:

```bash
npm install
cp .env.example .env
docker compose up -d
npm run migration:run
npm run seed          # необов'язково
npm run start:dev
```

## Тести

```bash
npm run test:e2e
```

Тести працюють із реальним PostgreSQL, тож база має бути піднята (`docker compose up -d`). Вони використовують окрему базу `<DB_NAME>_test` (`cinema_test`): її створює `test/global-setup.ts`, а сам набір на початку скидає її й застосовує всі міграції з нуля. Робоча база `cinema` не чіпається.

Набір (`test/app.e2e-spec.ts`) піднімає застосунок із `AppModule` (з тим самим `ValidationPipe`, фільтром винятків і серіалізатором) і через `supertest` перевіряє: маршрути та статуси 400/404/409, фільтри, сортування й пагінацію сеансів, формат відповіді з помилкою, транзакційність бронювання (409 без часткового запису, перевірка рядків у таблицях), одночасні запити на одне місце, унікальний індекс на рівні бази, каскадне видалення місць, 409 без тексту помилки бази.

## Перевірка запитами

Файл `requests.http` у корені містить запити до всіх маршрутів і до кожної описаної помилки.
Він написаний для розширення [REST Client](https://marketplace.visualstudio.com/items?itemName=humao.rest-client) у VS Code: виконуй запити послідовно згори вниз (`Send Request` над кожним).
Ідентифікатори підставляються зі змінних з відповідей попередніх запитів (`{{createFilm.response.body.id}}` тощо), вручну нічого вписувати не треба.
Дати сеансів стоять у 2099 році, тому файл не «протухає», а назви залів рандомізовані, тому файл можна проходити повторно. Дані тепер лишаються в базі між запусками, тому списки й `total` при повторі містять дані попередніх проходів.

## Структура

```
docker-compose.yml   PostgreSQL для розробки
src/
  main.ts            запуск, Swagger на /docs
  app.module.ts      корінь: ConfigModule, TypeOrmModule, глобальні ValidationPipe, фільтр винятків, серіалізатор
  data-source.ts     DataSource для TypeORM CLI і seed
  seed.ts            засівання бази (npm run seed)
  config/            клас змінних оточення з валідацією
  database/          спільні параметри підключення (застосунок, CLI, seed)
  migrations/        міграції схеми
  common/            спільне: pipe для :id, глобальний фільтр винятків, DTO помилки, помічники для помилок PostgreSQL
  films/             фільми
  halls/             зали, обчислення переліку місць
  showings/          сеанси, пагінація, фільтрація й сортування розкладу (Query Builder)
  bookings/          бронювання (таблиці bookings і booking_seats), схема місць сеансу
```

Кожен модуль має контролер, сервіс, DTO в `dto/` і класи сутностей TypeORM в `entities/`. Сервіси працюють через репозиторії, підключені до модуля (`TypeOrmModule.forFeature`).
Модулі звертаються один до одного лише через експортовані сервіси:

- `ShowingsService` використовує `FilmsService` і `HallsService` (перевірка існування фільму й залу);
- `BookingsService` використовує `ShowingsService` і `HallsService` (сеанс із залом, перелік місць).

Циклів залежностей між модулями немає. «Охоронці видалення» з ДЗ №1 більше не потрібні: заборону видаляти фільм чи зал із сеансами забезпечує зовнішній ключ.

## Модель даних

| Таблиця | Призначення |
| --- | --- |
| `films` | фільми |
| `halls` | зали (`name` унікальна, перелік місць не зберігається, обчислюється з `rows` і `seats_per_row`) |
| `showings` | сеанси: `film_id` і `hall_id` обов'язкові, ціна в копійках |
| `bookings` | бронювання: `showing_id` обов'язковий, `total_price` |
| `booking_seats` | одне місце одного бронювання на одному сеансі |

- Головне правило сервісу «одне місце на одному сеансі не можна продати двічі» тримає унікальний індекс на `booking_seats (showing_id, row, seat)`. Він описаний у класі сутності (`@Index(..., { unique: true })`) і створений міграцією. `showing_id` дублюється в `booking_seats` навмисне: індекс будується по колонках однієї таблиці.
- Зовнішні ключі: `showings.film_id` і `showings.hall_id` мають `ON DELETE RESTRICT`, `booking_seats.booking_id` має `ON DELETE CASCADE` (видалення бронювання видаляє його місця на рівні бази, сервіс місця не видаляє).
- Додаткові колонки: `created_at` у `films`, `halls` і `bookings` (порядок у списках, тобто порядок створення, як у ДЗ №1), `starts_at_input` у `showings` (див. нижче). Додаткові індекси: `showings (starts_at, id)` для сортування сторінок, `showings (film_id)`, `showings (hall_id)`, `bookings (showing_id)`, `booking_seats (booking_id)`.

## Рішення, які варто знати

- **Розподіл перевірок.** DTO (class-validator) перевіряють форму: наявність поля, тип, діапазон, формат, унікальність місць у масиві. Сервіси перевіряють правила, яким потрібен стан бази: існує чи фільм і зал, чи місце є в залі, чи є залежні сеанси, чи час у майбутньому. Правило «місце вільне» перевіряє сама база унікальним індексом.
- **`ValidationPipe`** глобальний (`whitelist` + `transform`): поля, яких немає в DTO, відкидаються й до сервісу не доходять.
- **Некоректний `:id`.** Усі id генеруються базою як UUID v4 (`gen_random_uuid()`, розширення `pgcrypto`, `uuidExtension: 'pgcrypto'`). Рядок, що не є UUID, неможливо знайти, тому `ParseUUIDPipe` повертає для нього 404, як і для невідомого id.
- **Єдиний формат помилок.** Глобальний `AllExceptionsFilter` (`APP_FILTER`) віддає для кожної помилки `{ "statusCode": 404, "message": "...", "path": "/films/..." }`. Для помилок валідації `message` це масив рядків. Поле `error` зі стандартної відповіді Nest (`"Not Found"`) більше не віддається. Непередбачена помилка (наприклад, обрив підключення до бази) дає 500 із загальним повідомленням, а подробиці лише пишуться в лог, тож текст помилки бази клієнту не потрапляє.
- **Час початку й фільтр `date`.** `startsAt` має містити і дату, і час у розширеному форматі (`2099-01-01T18:00:00Z`); голу дату чи базовий формат відхиляє DTO (400). Колонка `starts_at` має тип `timestamptz` і зберігає момент часу, а `starts_at_input` зберігає текст так, як його надіслав клієнт: `timestamptz` не пам'ятає зсув (`+03:00`), а API, як і в ДЗ №1, повертає `startsAt` саме в такому вигляді (`2099-06-01T01:00:00+03:00` повертається без змін). Значення без зсуву (`2099-01-01T18:00:00`) читається як UTC. Сортування й фільтр `date` працюють по `starts_at`. Межі доби в `date` теж UTC: `date=2099-05-31` залишає сеанси з `2099-05-31T00:00:00Z` до `2099-05-31T23:59:59Z`.
- **`GET /showings`.** Відповідь: `{ items, total, page, limit }`. `items` це сеанси поточної сторінки з `filmTitle` і `hallName` замість `filmId` і `hallId`; `total` це кількість усіх сеансів, що відповідають фільтрам; `page` і `limit` це застосовані значення. Параметри `page` (ціле від 1, за замовчуванням 1), `limit` (ціле від 1 до 100, за замовчуванням 20), `sort` (`asc` | `desc`, за замовчуванням `asc`), `filmId`, `date`; усі необов'язкові. Значення поза межами, не цілі числа й інший `sort` дають 400 (регістр важливий: `ASC` це 400). Сторінка за межами вибірки дає `items: []` з реальним `total`. Фільтри, сортування, `OFFSET` і `LIMIT` виконує один запит, зібраний через Query Builder, у застосунок потрапляють лише рядки сторінки. Порядок: за `starts_at` (`asc` або `desc`), а сеанси з однаковим часом завжди за `id` за зростанням, щоб сторінки не перетиналися. `filmId`, що не є UUID, нічого не знаходить (порожня сторінка), як і в ДЗ №1.
- **`GET /showings/:id`** віддає `filmTitle` і `hallName`. `POST /showings` повертає сеанс з ідентифікаторами `filmId` і `hallId`.
- **Бронювання «все або нічого».** Рядок у `bookings` і рядки в `booking_seats` пишуться в одній транзакції (`DataSource.transaction`, усередині неї працює `manager`). Якщо місце зайняте, унікальний індекс відхиляє вставку (код PostgreSQL `23505`), транзакція відкочується й у базі не лишається ні бронювання, ні жодного місця цього запиту. `try/catch` стоїть навколо виклику `transaction`, а не всередині колбека. Це працює й для двох одночасних запитів на одне місце: переможець один, інший отримує 409. У тексті 409 перелічені зайняті місця (запит до бази після відкату), текст помилки бази не потрапляє у відповідь. Межі залу (400) перевіряються до відкриття транзакції.
- **Місця в бронюванні** повертаються впорядкованими за рядом і місцем (у ДЗ №1 порядок збігався з порядком у запиті; у таблиці порядку немає).
- **Видалення фільму чи залу.** Сервіс видаляє рядок, а зовнішній ключ `ON DELETE RESTRICT` не дає видалити фільм чи зал із сеансами (код `23503`) і це стає 409 з поясненням причини. Сеанси разом із фільмом ніколи не видаляються. Невідомий id: 404.
- **Схема місць** `GET /showings/:id/seats` реалізована в `BookingsController`, бо обчислюється з бронювань, а `ShowingsModule` не повинен залежати від `BookingsModule`.
- Якщо тіло `POST /showings/:id/bookings` невалідне, а сеанс не існує, повертається 400, а не 404: `ValidationPipe` спрацьовує раніше за сервіс.
- Гроші: ціни та `totalPrice` у копійках, цілими числами (`integer`).
- Додаткові обмеження DTO, яких немає в завданні: `title` фільму до 255 символів, `releaseYear` від 1888 до 2100, назва залу до 100 символів, розмір залу до 1000 рядів і 1000 місць у ряду, не більше 1000 місць в одному бронюванні. Числа, що зберігаються в `integer` (`durationMinutes`, `price`), не більші за 2 147 483 647, а сума бронювання (`price` × кількість місць) не може перевищувати це значення (інакше 400), щоб база не відповіла помилкою переповнення.
- Назва залу унікальна без урахування регістру: «Hall 1» і «hall 1» вважаються однією назвою (409). Сервіс перевіряє це запитом `LOWER(name)`, а унікальне обмеження `halls.name` у базі (чутливе до регістру) ловить гонку двох однакових запитів, і вона теж стає 409.
